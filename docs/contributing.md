# Contributing and building documentation

Source, issues and reviewable changes live in the
[JupyHop repository](https://github.com/uibcdf/jupyhop). Contributions are MIT
licensed. The [contributor guide](https://github.com/uibcdf/jupyhop/blob/main/CONTRIBUTING.md)
describes client setup, tests and isolated SSH/Jupyter fixtures.

## Build the public documentation

Use Python 3.14 for the documentation toolchain. From a source checkout, create
the dedicated environment with mamba:

```console
mamba env create -n jupyhop-docs --file devtools/conda-envs/docs_env.yaml
mamba activate jupyhop-docs
python -m pip install --no-deps --no-build-isolation -e .
make -C docs check
```

Alternatively, in an existing Python 3.14 virtualenv, install the documentation
extra from the checkout using `python -m pip install -e '.[docs]'`.
Documentation tools are build-time dependencies; the installed client remains
free of mandatory Python-package dependencies.

The check target builds HTML with references and warnings treated as errors, then
verifies local links, fragments, resources and generated CLI coverage. It also
parses standalone fenced JupyHop examples with the actual CLI parser, validates
fenced TOML against the config reader and decodes fenced JSON. This catches
misspelled options, invalid profile fields and malformed output examples in CI.
Shell examples are not executed; remote prerequisites and authentication still
need their isolated integration/acceptance checks. Output is in `docs/_build/html`.
Preview it locally:

```console
python -m http.server 8000 --bind 127.0.0.1 --directory docs/_build/html
```

Open the printed local address in your browser and stop the preview with Ctrl-C.
The build does not execute SSH/Jupyter examples or notebooks. CLI help is
generated by constructing the real parser, without invoking its commands.

`make -C docs linkcheck` optionally checks external links and requires network
access. Its results can include upstream service errors; keep those observations
distinct from local-reference and build acceptance.

## Write guides that match the release

Use MyST Markdown in `docs/`. Describe implemented behavior and supported
platforms; keep roadmap proposals labeled as future work. Prefer task-oriented
examples with generic aliases/domains and existing-environment placeholders.
Never commit real infrastructure details or credentials.

Reference pages may explain CLI/JSON contracts, while the tutorials should lead
to a usable existing or managed session. Keep their ownership and lifetime
distinction explicit. The [developer guide](https://github.com/uibcdf/jupyhop/tree/main/devguide)
contains design decisions, experiment reports and acceptance evidence.

## Keep the first-use experience useful

For each task, say where to run its commands, which values to replace, what
success looks like and what to do next. Prefer names and terminal choices for
human workflows; retain exact UUIDs for scripts and uncertain-operation recovery.
Keep optional profiles and implementation details in the deeper guides.

Every public Markdown page has a short, distinct description in its MyST
`html_meta` front matter, including a matching Open Graph description. The shared
layout supplies preview titles/URLs and the local share image. Update those
summaries when a page's purpose changes; inspect rendered desktop/mobile pages,
keyboard focus, light/dark colors and image alternatives after presentation changes.

To regenerate the notebook image, share card and normalized menu transcript,
use the development environment with the experiments dependencies, OpenSSH
server/client, tmux and Chrome installed. From the checkout, run:

```console
python -m experiments.docs_assets
```

The experiment uses private loopback SSH/Jupyter fixtures and a fresh sandboxed
browser profile. It executes the Quickstart's harmless cell, checks its result,
captures JupyterLab and verifies a two-session management menu. It replaces only
`first-notebook.png`, `share-card.png` and `session-menu.txt` in `docs/_static/`.
It closes its own processes and never uses real SSH destinations. Review the
assets for identifiers/credentials before committing them, then rebuild the site.
These checks do not substitute for an unassisted walkthrough with new readers.

## Publication

Pull requests build and validate the site without deployment. Pushes to main and
manual dispatch can publish a validated Pages artifact using the GitHub Pages
environment. Generated HTML stays outside source branches. Deployment requires
the build/check job to succeed; it does not republish Conda packages or create
version tags.

The [release guide](releasing.md) covers package artifact inspection and the
separately authorized Conda workflow.
